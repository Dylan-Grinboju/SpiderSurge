# Building and releasing

`dotnet build -c Release` makes `bin/Release/net472/SpiderSurge.dll`. The version comes from the latest `vX.Y.Z` git tag through [MinVer](https://github.com/adamralph/minver), so the code holds no version number to edit. A build after `v1.0.0` is `1.0.1-dev.N`, and the update check counts it as older than the release with the same number. A build after a beta tag such as `v1.0.0-beta.1` is `1.0.0-beta.1.N`, which the update check treats as a beta. A build without the git history (a source zip) is `0.0.0-dev`. Only GitHub Actions makes release builds: a build made anywhere else ends in `+local`, even on a release tag (`1.0.0+local`), so runs from testing can be told apart in telemetry.

To release, first update `README.md` and the linked part guides to describe the new release. Write the release notes in a draft GitHub release for the new `vX.Y.Z` tag, without publishing it, then push that tag on the release commit. The Build workflow builds `SpiderSurge.dll` from the tag, attaches it to the draft and publishes the release; with no draft, it publishes one with GitHub's generated notes. The update check reads the recently published releases and offers the newest one, so players are offered the new version once it is published, which is only after its DLL is attached; drafts are never offered. `version.txt` is only for players on 0.4.0 or older, whose update check reads it from `main`. Set it to the first release made this way once that release is published, then leave it.

A beta is released the same way with a `vX.Y.Z-beta.N` tag, such as `v1.0.0-beta.1` for the first beta of 1.0.0; README.md stays as it is. The workflow publishes it as a pre-release, and the update check offers pre-releases only to players whose installed DLL is a beta, ordered as in SemVer: `1.0.0-beta.2` follows `1.0.0-beta.1`, and `1.0.0` follows every `1.0.0` beta. Players on a release are not told about betas. Give testers the beta DLL from its release page to start.
